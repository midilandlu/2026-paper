# AI 原生 SDLC 實戰手冊 — 精要導讀

> 這是 Anthropic〈The AI-native SDLC playbook〉的**繁體中文重點整理**，以自己的架構重新歸納核心觀念、設計判準與導入順序，**不是原文翻譯**。原文約 40 分鐘閱讀量，每個做法都附有完整步驟、範例檔案與設定，官方另提供 PDF 版供團隊分享。實作時請直接閱讀原文：
> <https://claude.com/resources/articles/the-ai-native-sdlc-playbook>

## 1. 一句話版本

AI 讓「寫程式」從最慢的階段變成最快的階段，但審批、審查、交接這些**圍繞程式碼的流程**還停留在人的速度。這份手冊主張：保留舊流程的**控制目標**，但把**執行方式**改造成一個由交付物串起來、由 agent 推動、由人在關卡上把關的迴圈。

## 2. 問題出在哪

傳統 SDLC 的重量是為「寫程式最貴」的時代設計的；PRD、估點、安全審查，都是為了在漫長開發期中強迫對齊。當 Build 縮到幾小時，會發生三件事：

| 現象 | 意思 |
|---|---|
| 瓶頸外移 | Plan、Review/Test、Deploy 仍以人速運行，變成新的瓶頸 |
| 控制失效 | 逐行人審在 agent 寫掉大半 diff 後跟不上 |
| 治理變貴 | 例外仍要排進每週／每月的委員會 |

原文的例子很直接：安全團隊的人力是按人的產出配置的，agent 把產量放大後，不是佇列爆掉就是審查不足——受監管的組織兩個都不能接受。

## 3. 核心架構：交付物鏈

整份手冊最重要的一個概念：**每個階段結束時，把一份交付物提交進版控；下一個階段從讀它開始。**

```
intent.md → spec.md → plan.md → diff + 測試 → PR + 審查發現 → 事故紀錄 ─┐
    ↑                                                                    │
    └──────────────── 控制帶突破時，寫出下一份 intent.md ◄───────────────┘
```

這帶來三個好處：

- **人與 agent 讀寫同一份檔案**，前段用 markdown 正是為了這點
- **commit 串本身就是稽核軌跡**：誰要求、agent 產出什麼、誰核准
- **交付物被接受 = 觸發下一關**，最終讓流程可以自動接力

人並沒有被移出流程，而是**從「每階段從零開始做」移到「在關卡上審查 agent 標記出來的東西」**。

## 4. 六階段速覽

| 階段 | 交付物 | 關鍵做法 | 人在哪裡把關 |
|---|---|---|---|
| **Plan** | `intent.md` | 非工程師也能跟 Claude brainstorm，用自己的話把想法寫成 proto-spec | 產品負責人接受或退回 |
| **Design** | `spec.md` | 需求與設計在一次工作階段完成，以組織 skills 為約束，並**主動標示政策衝突** | 產品負責人審閱（不撰寫）、疑慮交給政策負責人 |
| **Build** | `plan.md` + 程式碼 | 預設從 plan mode 開始；`CLAUDE.md` 承載團隊知識；平行 worktree 與 subagents | 工程師接受計畫；高風險交技術主管 |
| **Test** | 測試輸出 | 給 agent 自我驗證迴路；設定變更觸發 evals | code owner 看附上的證據 |
| **Deploy** | PR + 審查發現 | AI 雙向參與審查；hooks 當審批關卡；CI/CD 按環境分級自治 | branch protection、發版經理 |
| **Maintain** | 新的 `intent.md` | 確定性監控觸發 Claude 診斷；排程安全掃描；頻道內值班 | 服務負責人分流 |

幾個值得特別記住的細節：

- **Plan mode 自己就是一道關卡**：接受計畫前 Claude 無法改檔案，所以設計審查一定發生在程式碼產生之前。
- **`CLAUDE.md` 要短**：每次都會整份讀進 context。同一個錯犯兩次才寫進去。
- **修 bug 先寫會失敗的測試並提交**，再讓 agent 在不准改測試的前提下修好它——這才是「bug 已消失」的證明。
- **evals 要測的是「駕駛 agent 的設定」**：`CLAUDE.md`、skills、hooks 一變更就跑；每個 production 事故都要變成一個 eval。
- **回滾是最需要演練的路徑**，因為最後一階段的自主迴圈會依賴它。

## 5. 治理的三層結構

這是全文最實用的一組判準：

| 層 | 性質 | 作用 | 誰能關掉 |
|---|---|---|---|
| **Skills** | 建議性 | 讓 agent 在寫的當下就套用政策 → 違規**變罕見** | 工作階段可能不遵守 |
| **Hooks** | 確定性 | 每次動作都檢查，可 allow／ask／block → 違規**幾乎不可能** | 團隊層可改；managed 層不可 |
| **Managed settings** | 組織強制 | 權限、沙箱、憑證隔離、只允許核准來源的 plugin／MCP | 工程師無法覆寫 |

判斷原則：

- **必須永遠成立的政策，不能只靠 skill**，背後要有 hook 或 PR 審查重新檢查。
- **build 期間的 hook 要快、只看被改動的檔案**；會要求人核准的 hook 屬於部署關卡，否則會把人放回所有平行工作階段的關鍵路徑上。
- **權限規則管不到 shell**：工具層禁了網路，shell 指令照樣連得出去，所以需要 OS 層沙箱；同理，憑證檔也要在沙箱層額外封鎖。
- 原文提供的受監管企業設定範例，作者明確說是**用來裁剪的起點，不是照抄的範本**——每一條禁止都在拿能力做交換。

## 6. 自主迴圈怎麼閉合

最後一階段的設計很值得參考，因為它示範了「讓 agent 自主但不失控」的分寸：

1. **偵測完全不用模型**：確定性腳本以滾動基線監看單一指標
2. **分級授權**：輕微偏離只記錄；中度偏離讓 Claude 唯讀診斷；嚴重偏離才允許行動，而且**只能開 PR 或觸發事先核准的 runbook**
3. **輸出回到起點**：診斷寫成 `intent.md`，跟其他想法一樣走完整條流程
4. **人只負責分流**：修、排程、或駁回；駁回同時用來調校門檻

同樣的模式也套用在排程安全掃描（掃描結果走一般審查關卡，不直接上線）與聊天頻道值班（頻道歷史本身就是稽核紀錄）。

## 7. 怎麼衡量

每個做法都配一組領先與落後指標，而且**全部取自既有系統**——git history、PR metadata、CI、OpenTelemetry、事故追蹤——不需要另建儀表板。挑幾個代表性的：

| 面向 | 看什麼 |
|---|---|
| 需求速度 | 從第一次對話到 `intent.md` 提交的時間 |
| 規格品質 | Build 開始後還有多少需求返工 |
| 計畫品質 | 第一次實作就 merge 的比例 |
| 知識沉澱 | Claude 重複犯同一個錯的頻率 |
| 驗證效果 | agent 變更的首次 CI 通過率 |
| 審查效率 | 到首次審查的時間；無需人介入就解決的留言比例 |
| 迴圈健康 | 同類事故的重複發生率 |
| 整體交付 | DORA 指標 |

## 8. 導入順序

原文的每個做法都標了前置條件，可依此排出波次（以下為本文整理）：

| 波次 | 內容 | 理由 |
|---|---|---|
| 0 | `CLAUDE.md`、plan mode、自我驗證迴路、`intent.md` 模板 | 沒有前置條件，是所有後續的地基 |
| 1 | 把一條執行不一致的政策寫成 skill；需求與設計工作階段 | 依賴第 0 波 |
| 2 | hooks、AI 審查迴圈、連續 evals | **關卡要先於自動化就位** |
| 3 | CI/CD 整合、平行工作階段、auto mode | 需要可靠的關卡與審查 |
| 4 | 自主監控迴圈、排程掃描、頻道值班 | 需要已驗證的回滾路徑 |

導入節奏：**先手動逐步提示，確認每一關可靠後，才把「交付物被接受」接成下一關的自動觸發。**

## 9. 給自己的筆記

- 這份手冊本質上是在回答「**當程式碼變便宜，什麼還需要人？**」——答案是判斷與核准，而它把這兩件事集中到明確的關卡上。
- 它能說服受監管組織的關鍵不是速度，而是**證據來自工具鏈**（測試輸出、build log、PR 紀錄），而不是 agent 的自述。
- 與既有系統（Jira、需求追溯工具）並存時，原文的建議是**每種交付物只指定一個權威來源**；做不到就至少雙向互連。
